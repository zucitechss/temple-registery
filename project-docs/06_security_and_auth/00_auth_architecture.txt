1. PURPOSE

   Document the full authentication architecture: JWT token lifecycle,
   MFA implementation, Aadhaar eKYC flow, session management, and the
   Spring Security filter chain.

3. DETAILED CONTENT

   3.1 AUTHENTICATION FLOW

   Step 1: POST /api/auth/login { username, password }
     - Load user by username
     - Verify is_active = true
     - Check locked_until (if in future, return 423 with retry_after)
     - Verify bcrypt password hash
     - On failure: increment failed_login_count; if >= 5, set locked_until
     - On success: proceed to Step 2

   Step 2: MFA Challenge
     - If mfa_type = TOTP: return { mfaRequired: true, challengeType: "TOTP" }
     - If mfa_type = SMS_OTP: generate OTP, send via notification channel,
       return challengeType: "SMS_OTP"
       LOCAL DEV NOTE: SMS_OTP path logs the OTP to the application console
       (SmsGateway mock); no real SMS is sent. Use TOTP for all local testing.
     - Frontend presents MFA input screen

   Step 3: POST /api/auth/mfa-verify { tempToken, mfaCode }
     - Verify MFA code (TOTP: compare with current window ±1 step;
                         SMS_OTP: compare with stored OTP + expiry check)
     - On success: issue access token + refresh token
     - On failure: log to audit_auth_events; count MFA failures separately

   Step 4: Token Response
     { accessToken, expiresIn: 7200 }
     - accessToken: RS256 JWT, 2-hour TTL (app.jwt.access-token-expiry-ms,
       application.yml)
     - refreshToken: opaque UUID, stored as SHA-256 hash in DB
     - DECISION (RESOLVED, corrected H-1 — superseded the block below as
       originally written; production is cross-origin, not same-origin):
       BOTH accessToken and refreshToken are stored in HttpOnly cookies
       (AuthController.addCookie), not one cookie plus response-body/memory
       storage as originally planned here.
       Cookie attributes: HttpOnly; Secure; SameSite=None; Path scoped per
       cookie (/api/v1 for access_token, /api/v1/auth/refresh for
       refresh_token).
       SameSite=None, not Strict: the SPA (Vercel) and the API (Render) are
       different origins, so a Strict or Lax cookie would never be sent on the
       SPA's own cross-origin requests. See HLD §11.1a for the topology.
       CSRF analysis (revised — H-5): SameSite=None on its own provides NO
       CSRF protection, cross-origin or same-origin. Every unsafe method
       (POST/PUT/PATCH/DELETE), including /api/v1/auth/refresh, requires a
       stateless double-submit token: the value of the readable XSRF-TOKEN
       cookie echoed back in the X-XSRF-TOKEN header (CookieCsrfTokenRepository
       in SecurityConfig). This is enforced for every endpoint, with no
       exemption for login, MFA, refresh or logout.
       The Authorization: Bearer header path in JwtAuthenticationFilter is a
       genuine second entry point, but it is for non-browser API clients
       (E2E tests, scripts) — the SPA itself is cookie-only and never stores
       either token in memory, Redux or any browser storage.

   3.2 TOKEN REFRESH FLOW

   POST /api/auth/refresh
     - Read refreshToken from HttpOnly cookie (NOT request body)
     - Hash the provided token with SHA-256
     - Lookup in refresh_tokens WHERE token_hash = :hash AND revoked_at IS NULL
     - Verify expires_at > NOW()
     - Verify user is still active and not locked
     - Check token_revoked_before: if token issuedAt < user.token_revoked_before -> 401
     - Rotate: revoke old token (set revoked_at), issue new token pair
     - Return new { accessToken } in body; set new refreshToken in HttpOnly cookie

   3.3 SPRING SECURITY FILTER CHAIN

   Order:
   1. CorsFilter (allow frontend origin)
   2. JwtAuthenticationFilter (validate access token; set SecurityContext)
   3. SessionManagementFilter (stateless; no session created)
   4. ExceptionTranslationFilter
   5. FilterSecurityInterceptor (@PreAuthorize evaluation)

   JwtAuthenticationFilter:
   - Extract Bearer token from Authorization header
   - Verify RS256 signature using public key
   - Check claims: exp, sub, role
   - Load user record from DB (or cache); check user.is_active = true
   - Check token_revoked_before: if (tokenIssuedAt < user.tokenRevokedBefore) -> return 401
     This enforces immediate token revocation when SUPER_ADMIN transfers a DC's district.
   - Build UsernamePasswordAuthenticationToken with authorities from role claim
   - Set in SecurityContextHolder

   3.4 AADHAAR eKYC FLOW (REGISTRATION ONLY)

   Used only during initial user registration, not for every login.

   Step 1: User enters Aadhaar number on registration form
   Step 2: POST /api/auth/aadhaar-otp-request { aadhaarNumber }
     - Forward to UIDAI OTP API (or mock for dev)
     - Store masked Aadhaar (last 4 digits) temporarily in session
   Step 3: User enters OTP received on Aadhaar-linked mobile
   Step 4: POST /api/auth/aadhaar-otp-verify { transactionId, otp }
     - UIDAI verification response confirms identity
     - Store aadhaar_encrypted (AES-256) in users table
     - Complete registration

   3.5 TEMP TOKEN LIFECYCLE (between login and MFA verify)

   When a user submits valid username/password via POST /api/auth/login but MFA is
   required, the server does NOT issue a full access token. Instead it issues a
   short-lived TEMP TOKEN.

   Format: Short-lived RS256 JWT (same signing key as access tokens)
   Claims: {
     "purpose": "MFA_CHALLENGE",
     "sub":     "123" (user ID as string),
     "iat":     epoch,
     "exp":     iat + 300  (5-minute TTL)
   }
   Return channel: Response body JSON field "tempToken" (NOT a cookie)
   Frontend storage: In-memory variable ONLY (same as access token). Never
     persisted to localStorage, sessionStorage, or cookie.
   Usage: Sent as Authorization: Bearer <tempToken> on POST /api/auth/mfa-verify
   On expiry: server returns HTTP 401 TRM-AUTH-001; user must restart login flow.

   JwtAuthenticationFilter MUST reject temp tokens on all endpoints EXCEPT
   /api/auth/mfa-verify and /api/auth/mfa-setup/confirm. A request bearing a
   temp token to any other endpoint returns 401 Forbidden.

   Guard in MfaVerificationService:
     1. Parse JWT; assert claims.purpose == "MFA_CHALLENGE"
     2. Assert token not expired (exp > NOW)
     3. Assert no matching row in token_revoked_before (user not transferred mid-session)
     4. Proceed to TOTP/recovery-code verification

   3.5a MFA SETUP FLOW (new users + re-enrollment)

   Triggered when: (a) user.mfa_type IS NULL (never configured MFA), or
                   (b) user.mfa_reenrollment_required = 1 (recovery code used).

   RE-ENROLLMENT ENFORCEMENT:
   After successful login (access token issued), JwtAuthenticationFilter checks
   the users.mfa_reenrollment_required flag. If true:
     - Allow all GET requests to proceed (read-only access preserved)
     - Block all write methods (POST, PUT, PATCH, DELETE) except /api/auth/mfa-setup*
     - Return HTTP 403 with body:
       { "error": "MFA_REENROLLMENT_REQUIRED",
         "message": "Please re-configure MFA before performing write operations.",
         "setupUrl": "/api/auth/mfa-setup" }

   MFA SETUP ENDPOINT FLOW:
   POST /api/auth/mfa-setup  (Authenticated; requires valid access token)
   Guard:  Reject if user.mfa_enabled = 1 AND user.mfa_reenrollment_required = 0
           (prevents accidental reset of working MFA)
   Service logic:
     1. Generate 20-byte cryptographically random TOTP secret (SecureRandom)
     2. Base32-encode the secret
     3. Encrypt secret via AesEncryptionConverter; store in users.mfa_secret_encrypted
        (at this point MFA is NOT yet activated — mfa_enabled stays unchanged)
     4. Generate a setupToken: short-lived RS256 JWT (claims: purpose=MFA_SETUP,
        userId, exp=NOW+600s)
     5. Build QR code URI:
        otpauth://totp/TRM:{username}?secret={base32secret}&issuer=TRM&algorithm=SHA1&digits=6&period=30
     6. Return:
        { "totpSecret": "{base32secret}",
          "qrCodeUri":  "otpauth://totp/TRM:{username}?secret=...",
          "setupToken": "{setupToken}" }
   NOTE: The TOTP secret is shown ONCE here so the user can manually enter it if
   QR scan fails. It is never returned again after the confirm step.

   POST /api/auth/mfa-setup/confirm  (Authenticated)
   Request: { "setupToken": "string", "mfaCode": "6-digit string" }
   Guard:   Validate setupToken (purpose=MFA_SETUP, not expired, userId = caller)
   Service logic:
     1. Retrieve mfa_secret_encrypted from DB; decrypt to base32 secret
     2. Validate mfaCode against current TOTP window (allow 1 step tolerance = ±30s)
     3. On success:
          UPDATE users SET mfa_enabled = 1, mfa_type = 'TOTP',
                           mfa_reenrollment_required = 0  WHERE id = :userId
          Mark all existing mfa_recovery_codes used_at = NOW() (invalidate old set)
          INSERT 8 new rows into mfa_recovery_codes (bcrypt-hashed)
          Invalidate setupToken (INSERT to block-list or short expiry is sufficient)
     4. Return plaintext recovery codes ONCE:
        { "recoveryCodes": ["aaaa-1111", "bbbb-2222", ...8 items],
          "message": "MFA configured. Store these recovery codes safely.
                      They will not be shown again." }
   On incorrect TOTP code:
     - Return HTTP 400 TRM-AUTH-006: "Invalid MFA code during setup"
     - Increment failed_setup_attempts counter (max 5; lock setup after 5 failures)
     - Do NOT activate MFA (users.mfa_enabled stays unchanged)

   3.6 MFA RECOVERY CODE FLOW

   Used when a user cannot access their primary MFA device (lost TOTP authenticator,
   phone replacement, etc.). Recovery codes are generated at MFA setup time.
   See schema: 04_schema_design/11_user_auth_schema.txt (section 3.4 mfa_recovery_codes).

   POST /api/auth/mfa-verify { tempToken, mfaCode, isRecoveryCode: true }
   Service logic:
     1. Load all unused recovery codes for user (mfa_recovery_codes WHERE used_at IS NULL)
     2. For each: if (bcrypt.verify(submittedCode, row.code_hash)) -> MATCH
     3. On match: UPDATE mfa_recovery_codes SET used_at = NOW() WHERE id = :rowId
     4. Issue access token + refresh token (same as normal MFA success)
     5. Log to audit_auth_events (event_type = 'MFA_RECOVERY_USED')
     6. Set user.mfa_reenrollment_required = 1 (require TOTP re-setup on next session)
     7. Insert SUPER_ADMIN in-app notification: "Recovery code used for {username} at {ip}"
   On failure (no matching code or all codes used):
     - Return HTTP 401 with error TRM-AUTH-010: "No valid recovery codes available.
       Contact HR&CE system administrator."
     - Log to audit_auth_events (event_type = 'MFA_FAILURE', reason = 'RECOVERY_CODE_INVALID')

   GET /api/auth/recovery-codes  (Authenticated; any role)
   - Returns count of remaining unused codes only (not the codes themselves)
   - Used by frontend to warn users when codes are running low (< 3 remaining)

   POST /api/auth/recovery-codes/regenerate  (Authenticated; requires current MFA pass)
   - Requires MFA re-verification before regenerating
   - Marks all existing codes used_at = NOW() (invalidates old set)
   - Generates 8 new codes; returns them ONCE in response body (shown once in UI)

   3.7 DISTRICT TRANSFER TOKEN REVOCATION FLOW

   See: 04_schema_design/11_user_auth_schema.txt (TOKEN_REVOKED_BEFORE section)
   API: PATCH /api/admin/users/{userId}/district  (SUPER_ADMIN only)
   Service atomically:
     1. UPDATE users SET district_id = :newDistrictId, token_revoked_before = NOW(6)
     2. UPDATE refresh_tokens SET revoked_at = NOW(6) WHERE user_id = :userId AND revoked_at IS NULL
     3. INSERT audit_data_events (table=users, operation=UPDATE, action=DISTRICT_REASSIGNMENT)
   Effect: All existing JWT access tokens for this user become invalid on next request.
   The user must re-login and will receive a JWT with the new district_id claim.

   At API layer (registration + password change):
   - Minimum 10 characters
   - At least 1 uppercase letter
   - At least 1 lowercase letter
   - At least 1 digit
   - At least 1 special character (!@#$%^&*...)
   - Not equal to username
   - Not one of last 5 passwords (store hashes of last 5)

   DTO validation: @ValidPassword (custom JSR-380 constraint)
   Server-side only; frontend may replicate but backend is authoritative.

4. DECISIONS LOCKED

   - RS256 (asymmetric) for JWT signing; private key supplied via the
     APP_JWT_PRIVATE_KEY / APP_JWT_PUBLIC_KEY environment variables (PEM
     contents, C-1) — platform-agnostic, not tied to a specific secret store;
     local dev alternative: classpath resource /keys/jwt-private.pem excluded
     from git via .gitignore
   - Access token: 2-hour TTL; Refresh token: 7-day TTL, single-use rotation
   - MFA is mandatory for ALL users; no bypass endpoint exists
   - Aadhaar eKYC only at registration; not at every login
   - RESOLVED (corrected H-1): BOTH access token and refresh token stored in
     HttpOnly cookies (SameSite=None; Secure) — production is cross-origin
     (SPA on Vercel, API on Render), so Strict/Lax would never be sent on the
     SPA's own requests. CSRF is a stateless double-submit token instead (H-5),
     not a property of SameSite. See Section 3, Step 4.
   - RESOLVED: token_revoked_before enforced in JwtAuthenticationFilter; DC district transfer invalidates tokens instantly
   - MFA recovery codes: 8 codes generated at setup; bcrypt-hashed; single-use; force re-enrollment after use
   - RESOLVED: mfa_reenrollment_required = 1 blocks all write operations (except /api/auth/mfa-setup*) at filter layer. User is shown a banner on login that explains they must re-configure MFA. Reenrollment is done in the same session via the MFA setup flow (see Section 3.5a).
   - RESOLVED: Temp token between login and mfa-verify is a 5-minute RS256 JWT with purpose=MFA_CHALLENGE claim. Frontend holds it in memory only (see Section 3.5).

5. OPEN QUESTIONS

   - RESOLVED: refreshToken is stored in HttpOnly cookie (see Decision above).
   - RESOLVED: UIDAI eKYC is used only at registration (not login). Sandbox/mock environment used for dev; production integration requires procurement from NeSL or UIDAI RES partner.
   - RESOLVED: mfa_reenrollment_required triggers an enforced re-enrollment flow. Writes are blocked (HTTP 403) until MFA is re-configured via /api/auth/mfa-setup. See Section 3.5a.

6. RISKS & EDGE CASES

   - Refresh token rotation means a network error between token issue and
     client receipt results in the client having neither old nor new token.
     Implement a grace window: the old token remains valid for 60 seconds
     after rotation to allow for retry.
   - RS256 private key compromise: generate a new keypair and rotate the
     APP_JWT_PRIVATE_KEY / APP_JWT_PUBLIC_KEY values immediately; all active
     tokens become invalid (users re-login).
   - Pre-signed document URL TTL: 15-minute TTL may be insufficient for
     large PDF downloads over slow rural/government network connections.
     MITIGATION: Frontend generates the download token immediately before the
     user clicks "Download" (not when the page loads). This starts the 15-minute
     window at the right time. The download request begins within seconds of URL
     generation; the TTL covers the actual transfer.
   - Session expiry mid-form: If a user is filling in a large asset declaration
     form and their session expires, all unsaved data is lost. Frontend should
     auto-save DRAFT state every 60 seconds using PATCH /api/declarations/{id}.
   - Deactivated user receiving notifications: JOB-04 must filter
     recipient_user_id to only active users (is_active = 1) before sending
     EMAIL/SMS. IN_APP is also suppressed for deactivated users.

7. ASSUMPTIONS

   - All auth endpoints are under /api/auth/** (unauthenticated)
   - All other endpoints require a valid access token
   - Frontend stores neither token anywhere client-side (not memory, not
     localStorage); both access and refresh tokens are HttpOnly cookies
     (SameSite=None; Secure) — corrected H-1, see Section 3, Step 4
   - mfa_reenrollment_required column added to users table in future migration if needed
